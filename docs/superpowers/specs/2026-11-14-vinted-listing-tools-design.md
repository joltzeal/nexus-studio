网络查询未取得分类目录，不能把未登录 403 描述为接口不存在。

## 2. 方案与职责

比较三条路径：保留全程 AI 逐控件规划、业务工具执行并由 AI 辅助、
直接编排未验证的上传和发布 HTTP 接口。
采用业务工具方案；它复用现有 LangGraph、Playwright 和宿主边界，
减少固定动作的模型调用，也保留提交意图与结果核对。
接口直发缺乏完整协议证据，不纳入实施。

| 层              | 负责                                                       | 不负责                                   |
| --------------- | ---------------------------------------------------------- | ---------------------------------------- |
| Rust 协调器     | 准备与发布任务、资源配额、租约、SQLite、意图、回执、outbox | 分类名称、平台选择器或 Jev 提示词        |
| Ecom Agent      | 无浏览器内容准备、内部工具、Vinted 适配与模型策略          | 新建独立浏览器启动器                     |
| browser-runtime | 受控页面读写、同源 GET、定位、上传、读回                   | 存储账号业务资料或判断封禁语义           |
| 账号池          | 主页、账号事实、逐窗口登录观察、钱包、收款与分析           | 独占浏览器或在普通 HTTP 客户端复制登录态 |
| 商品库          | 可复用商品事实和平台分类资料                               | 执行平台发布                             |

工具可被工作流直接调用，也可包装为现有框架的类型化 tool。
不要求每次调用前再让 LLM 决定调用哪个工具，不额外引入 MCP 服务或 Agent 框架。
工具名称是插件内部接口设计，不能直接加入任意插件或 WebView 可调用的宿主白名单。

## 3. current 的解析和状态模型

### 3.1 保留原始错误分类

先在绑定浏览器中执行相对路径 GET，检查请求和响应同源且路径符合预期，
再解析有界 JSON。HTTP 状态、业务码和消息代码必须在错误分类前可见。
只接受已验证的响应，不允许跳转到其他站点后仍消费证据。

current 的判定顺序：

1. 请求或响应无法核实：返回检查失败，保留历史事实。
2. HTTP 200/401/403 的可解析 JSON 精确包含数值 `code: 106`
   和 `message_code: "access_denied"`：记录该窗口 `logged_out`。
3. 成功业务响应：读取 user，核对用户 ID 和绑定。
4. 身份不符：返回 `identity_mismatch`，不写入目标账号的新身份或资料。
5. 身份匹配且 `is_account_banned === true`：写入官方 `blocked`。
6. 身份匹配且未明确封禁：记录已登录，继续核对限制；不自动覆盖既有业务状态。

业务规则不依赖 message 的英文文本，不把字符串 `"106"` 或 HTML 中的同名文本当成该证据。
其他接口的 106 不修改 current 登录观察。
部分成功、缺少 user、未知数值状态或未理解的限制对象均不能推导为正常可写。

本次整理以用户给出的字段为支持契约，不新增旧字段别名读取。
已知 `is_blocked/is_banned/user.status` 的旧推断分支在替换后删除，
禁止继续维持两套封禁来源或在错误时让模型判断登录身份。

### 3.2 分开持久化登录与账号状态

账号池继续保有 `AccountStatus`。新增逐绑定窗口的观察，而不是把掉登塞入互斥枚举：

```ts
// 拟定契约；实现时统一维护公开 schema 和对应宿主校验。
type WindowSessionObservation = {
  windowId: string
  accountId: string
  bindingRevision: string
  observedAt: string
  source: 'official'
} & (
  | {
      status: 'authenticated'
      reason: 'current_user'
      platformUserId: string
    }
  | {
      status: 'logged_out'
      reason: 'current_access_denied'
      platformUserId: null
    }
)
```

只持久化这两种已核实观察；窗口没有有效观察时，界面派生为 `unknown`，
不为未检查、解绑失效或迁移后的窗口伪造官方观察。
`logged_out` 没有当前用户 ID，不能伪造已经认证过的身份。
宿主核对任务绑定和观察时的绑定修订后，才允许把该窗口掉登写入账号池。
较旧的不同操作不覆盖较新观察，重试同操作返回原回执。
网络错误保留上次确定观察及其时间，另外保存本次检查失败，不能刷新已登录的观察时间。

账号池在现有受控私有存储里保存逐窗口观察与幂等回执；
Rust 继续是 SQLite 唯一所有者，不为账号池另建 SQLite 客户端。
解绑或重新绑定会失效旧窗口观察，迁移副本默认未知，不能跨机器复制已登录结论。
账号状态、登录态、余额和模型分析分别记录新鲜度，不能使用单一最后更新时间覆盖四种事实。

新增任务状态 `login_required`，表示窗口等待重新登录，可复查恢复。
账号被明确封禁仍使用 `blocked`。
登录恢复只唤醒允许继续的未提交步骤；已存在发布意图或未知结果的条目只进行核对。
同账号其他健康窗口不因某个窗口掉登而改成 `login_required`；
它们仍受账号级互斥和未知提交保护约束。

### 3.3 主页、财务和商品读取

current 身份匹配后，把合法 `user.profile_url` 通过受控观察写入账号池 `homepageUrl`。
验证 HTTPS、市场及 `/member/<相同用户ID>`，同 ID 的昵称变化可更新，
空或非法值保留旧主页。和当前身份冲突时不改绑、不整条覆盖账号。
沿用已有主页订单查询调度，保留显式暂停和 Bark 设置。

新内部工具读取用户指定的三个接口：

- `account.readWardrobe`：同源 `/api/v2/wardrobe/{已核实ID}/items`，
  支持有界样本和有完整性标记的分页扫描，用于画像、发布基线和确认。
- `account.readWallet`：准确的
  `https://api.www.vinted.com/ledger/wallet/balance`，
  `main` 映射可用、`escrow` 映射待结算；两项独立保存金额、币种、来源和时间。
- `account.readBankAccounts`：准确的
  `https://api.www.vinted.com/payments/public/api/bank_accounts`，
  保存完整有效列表及默认标记，每个 user_id 必须与 current 相符。

两条财务 URL 与当前页面跨源。默认同源规则保留，新增通用且有界的宿主读取策略，
插件提供固定平台目标，宿主核对任务、origin、准确路径、GET 和预算；
browser-runtime 通过该窗口页面 fetch 与合法会话读取，使用 include 并遵守 CORS。
禁止任意绝对 URL、跨域通配、重定向、关闭浏览器安全或 Node HTTP 直连回退。
真实认证/CORS 尚未验证，失败时报告不可读，不改写成掉登或封禁。
财务结果写回前再次用 current 确认身份，核对失败不应用结果。

wardrobe 列表只保留有用商品投影，校验所有者及分页。
初始每页 5 项、单次最多 100 页或 500 项，并受截止时间约束。
保持 65,536 字节上限；降低 per_page 时从第一页重建扫描，
不能接着旧页码遗漏商品。达到预算、数据变化或读取失败时标记 partial，
不把样本或不稳定分页声称为账号全量商品。
样例的 `status` 是成色，关闭、隐藏、不可编辑不等于已售；
没有经过验证的售出证据时保留未知，不发明 closing action 映射。
列表不能提供描述、图片和唯一因果证据时，确认流程仍需补充详情。

余额改为两个独立 Money 观察，不用一个 currency 关联两项不同币种。
旧金额与各自证据在启动升级时一次性迁移；缺失、错误保留原值及旧时间，
不变成零。收款列表只有完整成功的 `[]` 才清空；
保留掩码账户号和字符串 routing number，不还原掩码、不丢前导零。
全部仍按用户约定明文持久化，不写 Keychain。

各观察分域维护新鲜度，以采集前预留的顺序控制迟到响应，
不靠人为递增 observedAt 突破当前全局时间门槛。
单项读取失败不撤销其他成功项，写入和稳定 operationId 回执同次落盘。
财务完整字段仅进入账号池，Agent 快照、画像、日志、toast 和普通检查点不包含银行资料。
详细字段、投影、预算与失败语义以[读取工具规范](../../49-vinted-account-read-tools.md)为准。

### 3.4 账号信息清洗与总结

以允许字段建立小型事实投影：身份、站点国家、币种、创建时间、自我介绍、
验证布尔值、公开商品与评价统计、已观察评分及限制证据。
身份和来源留给代码核对，AI 输入只包含完成本次判断需要的公开业务资料。
真实姓名、邮箱、生日、地址、第三方 ID、anon_id 和令牌不进入模型输入。

`account.inspectCurrent` 的结果不含余额。余额继续走独立工具；
余额不可用保留旧金额，不推测为零。
数值零和缺失/null 分开；字段名称不同的计数不相加为自创的销售统计。
收款账户、routing number 和姓名也不进入模型事实投影。

`account.summarize` 有两个输出：

- `factsSummary`：代码模板，复述已经验证的计数、验证状态等。
- `assessment`：Jev 的标签及概率，或用户开启后由现有生成模型写出的英文画像。

不能只靠 current 推断主营品类；这需要有界读取已有卖家商品和评价证据。
同一组证据的独立标签问题可放入同一次 Jev 请求。
模板可以消费选择结果；Jev 不用于生成任意文字。
模型结果失败不撤销已经保存的封禁或掉登事实，也不阻止其他账号的检查。
账号画像属于独立账号检查任务；发布任务不在占用窗口期间更新 AI 画像或做内容审核。

## 4. 本地分类和 Jev

### 4.1 数据与版本

本地兜底的唯一来源是插件打包内 `resources/vinted/us-catalogs.json`。
只接受已清洗的 schema 1；原始 API 大对象不增加运行时兼容读取。
静态目录没有账号、Cookie 或代理配置。
加载时校验范围、ID 唯一性、父子关系及内容 revision，再建立内存索引。
目录仅使用本地版本，不设置每次启动下载或自动线上回退。

构建将资源复制入插件发行目录，加密包中纳入逐文件摘要。
发行校验必须实际启动最终包并完成一次目录读取，
不能在开发态用源码路径可读代替打包完整性验证。
目录不可用时明确标记兜底能力不可用；不能据此改用在线目录，
也不能覆盖或否定已经核实有效的页面自动分类。

### 4.2 分类输入和结果

分类输入在浏览器执行前准备，包括商品 UUID、修订、已确认英文标题与描述、
用途和已有属性、目标市场及手动候选。图片识别候选与用户确认事实区分。
手动候选优先于本地 Jev 推荐，只验证有效性，不让模型自行替换。
它仍是页面为空时的兜底，不是可以覆盖网页自动推荐的强制分类。

本地兜底结果包含 `catalogId`、完整 `pathIds/pathTitles`、`catalogRevision`、
选择来源 `manual/jev`、模型与规则版本、候选判断及 `resolved/review_required/no_match`。
目录 ID 使用源数据的正整数，不让模型自己产生数字 ID。
同名节点不能合并，末级节点也不是账号发布许可。

商品平台资料使用以站点为范围的结构，保留通用商品分类的展示意义；
不把 Vinted 分类编号塞进现有 category 文本字段。
商品库持久平台资料和草稿引用都需修订控制，批次创建时复制到不可变快照。
普通文字编辑不能覆盖已有发布事实或取消重复上架保护。

最终分类在图片上传和网页推荐完成后才确认：

1. 读取页面实际分类 ID、完整路径及控件稳定性，排除占位和加载态。
2. 有有效页面值就保存为 `effectiveCategory.source: official_page`，不调用模型，
   不和预先兜底竞争，也不强制要求该 ID 存在于本地目录。
3. 页面最终为空时才应用已准备的兜底，记录其来源及 catalogRevision。
4. 两者均不可用或兜底不被页面接受时暂停补齐，不在窗口内临时请求分类模型。

准备回执记录真正生效的分类及表单证据；兜底快照与实际分类字段分开。
页面后来改变分类时使相关属性/准备回执失效，重新读回验证，
不能把预填的本地分类当作发布后的真实分类。

### 4.3 在执行前准备本地兜底

1. 代码提供当前层全部实际候选，使用短键映射真实 ID；本次最大候选数为 20。
2. 用 Jev Choice 选择，另以无匹配项或同请求中的适配性 Noul 表达没有合适分类。
3. 结果清晰时推进到下层；接近的前两条路径按宽度 2 保留，分别继续。
4. 到达叶节点后比较候选完整路径，重新检查商品与叶分类是否相符。
5. 代码验证返回键存在、路径连通、叶节点存在于固定版本；失败则待处理。

Choice 每题最多 255 个选项是当前上游限制，不是应用自己规定的目录最大值。
本地目录满足该限制，无需新增向量服务，也不需要把 2,916 节点一次塞给模型。
根到叶最多 5 次依赖层级；保留多分支或最终复核会增加问题数，不能承诺总共只调用 5 次。
相互独立分支的问题可同请求批量判断，依赖上一层的选择不能假装并行。

路径累计分数只能作为比较启发，不能当成校准后的最终正确率。
初始采用保守人工确认策略，收集标注商品后再确定自动采纳门槛；
不把当前通用 `reviewThreshold` 直接套用于每一种分类判断。
无匹配、用途含糊或材质不明时要求用户补齐，不因置信度高就允许编造事实。

缓存键包含商品事实摘要/修订、市场、目录 revision、模型配置摘要及规则版本；
不包含明文密钥。手动修改分类或本批次覆盖会使相关缓存失效。
任务中冻结目录 ID 和路径，插件目录更新不改变旧任务的分类。
冻结的内容属于兜底候选，不影响执行时沿用页面实际值。
页面没有自动分类且不接受兜底时，返回 `CATALOG_MISMATCH` 并暂停，
不联网覆盖目录、不自动换类目。

没有匹配或尚未确认的兜底不阻止内容已合格商品进入发布队列。
若真实页面也无法分类，再返回待补齐；因此不会为最终未使用的兜底强制增加审核。

## 5. 无浏览器内容准备与确定性发布

### 5.1 执行前内容准备

新增独立准备任务，读取不可变商品与本批次覆盖、真实图片内容，
完成图片审核、英文文案审核、必要改写和可选分类兜底。
它只取得模型与素材读取权限，不创建窗口、连接 CDP、取得浏览器 actor 或占用窗口并发。
不能伪造一个窗口任务来绕过当前 scope 校验。

Rust 持久化准备任务、模型用量和批准资料包引用。
现有模型配额与素材权限扩展为明确的准备任务 scope，不能放开无范围模型或文件访问。
准备时商品可已分配窗口，但分配不等于占用窗口租约；
只有内容通过并进入真正发布时才获取窗口与账号执行资源。

批准资料包至少绑定：

- 商品 UUID、修订、本批次有效覆盖摘要、目标市场和语言；
- 每张图片的内容摘要、顺序、可读取素材引用；
- 最终英文标题与描述、已确认属性和有界审核结果；
- 审核规则、模型配置摘要、可选兜底及其目录版本；
- 持久批准回执、完成时间和失效原因。

不把模型返回的一个 pass 布尔值当作跨修订可复用的永久许可。
同内容和审核上下文可在多个窗口复用结果；变更图片、标题、描述、相关属性或规则后失效。
模型凭据不进入缓存键。审核失败或保存失败不派发窗口，部分商品失败不阻塞其他已准备商品。
原始商品库文案不被批次改写自动覆盖。

发布阶段只验证该回执仍对应实际快照与素材，不再识图、审核文案、改写或请求分类模型。
发现资料缺失或需要内容改动时，在确认没有未知提交后暂停，
释放执行名额并返回准备；不能在已打开窗口的任务节点里继续模型审核。
正常 Post Listing 的窗口执行阶段模型调用数为零。

### 5.2 工具边界

| 内部工具                   | 输入                               | 输出或结果                       |
| -------------------------- | ---------------------------------- | -------------------------------- |
| `content.prepare`          | 商品与本批次覆盖、素材、审核策略   | 持久批准资料包或待处理原因       |
| `account.inspectCurrent`   | 绑定上下文，来源由宿主提供         | 认证、身份和业务状态的独立结果   |
| `account.readWardrobe`     | 已核实用户、模式与有界分页         | 商品投影、覆盖范围及完成性       |
| `account.readWallet`       | 已核实会话与固定目标策略           | 两项独立 Money 观察或不可读      |
| `account.readBankAccounts` | 已核实会话与固定目标策略           | 有效收款列表或不可读             |
| `account.summarize`        | 已验证事实及有界公开证据           | 事实模板、标签、可选画像         |
| `catalog.search`           | 市场、文字、父节点、分页           | 有界节点与完整路径               |
| `catalog.resolve`          | 商品快照、目录版本、手动选择       | 分类选择或待处理原因             |
| `listing.prepare`          | 批准资料、可选兜底、属性和素材引用 | 阶段进度、页面实际分类及准备回执 |
| `listing.verify`           | 冻结资料、当前页面及上传状态       | 完整读回或差异列表               |
| `listing.submit`           | 宿主认可的新提交意图和准备摘要     | 分派结果；不把点击成功当发布成功 |
| `listing.confirm`          | 稳定操作 ID、提交基线、商品和账号  | 确认事实或结果不明               |

工具上下文中的窗口、账号、站点和租约由宿主注入；
调用方不能传另一个 windowId、任意 Cookie、上传文件路径或任意 JS。
分类本地检索可不占浏览器资源，登录态读取和页面写入必须进入窗口 actor。
内容准备不使用该 actor；账号画像与财务完整刷新放在独立只读任务，
不塞进每个商品的发布流程。

账号池独立检查通过显式用户操作创建只读检查任务，使用受限 scope、
窗口和账号锁；不能伪造一个发布任务、绕过普通 `plugin_call` 限制或暴露无范围 browser RPC。
忙碌的窗口排队。需要启动环境时在检查入口明确显示；
本轮不规划自动登录、验证码处理或应用关闭后的后台系统服务。

### 5.3 prepare 的内部阶段

```text
open_form
  -> upload_images
  -> await_upload_and_page_recommendation
  -> read_effective_category
  -> apply_prepared_fallback_only_if_empty
  -> resolve_observed_controls
  -> fill_copy
  -> choose_observed_attributes
  -> fill_price
  -> verify_form
```

各阶段由代码定位实际控件，优先 label/role/testId 等可验证目标，
避免坐标、固定 sleep、模型虚构选择器或控件索引长期缓存。
平台及语言差异放在插件适配器；Rust 不维护分类和表单选择器。

`listing.prepare` 是逻辑业务工具，每次工作流推进只完成有界阶段，
完成后写检查点，并在阶段之间检查暂停、取消、账号观察和租约。
不把所有字段与最终发布塞进一个不可中断的长 RPC。

重启恢复先读回当前表单，确认阶段的外部效果后再执行；
上传超时不能直接重复添加所有图片，不能证明上传内容和数量时等待处理。
分类改变可能使品牌、尺码等控件重新渲染，先等实际控件和候选就绪再填写。
字段映射只使用已经取得的真实选项，缺少商品事实返回 `MISSING_REQUIRED_FACT`。
网页有效分类优先，包括本地目录没有的新分类；不能因为本地兜底更“有信心”而覆盖。
上传与推荐等待使用实际状态和有界截止时间，不能在图片尚未上传完成时把空值判为需要兜底。

现有 `select` 针对原生 SELECT，真实自定义弹窗需要明确的页面适配和测试。
本地目录只提供分类身份，无法补齐成色 ID、品牌、尺码、颜色或包裹选项。
支持常规已知弹窗；未适配页面返回 `FORM_CHANGED`，AI 可解释证据，默认不自动操作。

### 5.4 验证、提交与结果恢复

准备回执关联商品修订、分类版本、页面观测及素材摘要。
`listing.verify` 读回标题、描述、数值价格、币种、分类完整路径、
已确认属性及可验证上传状态，和批准资料及本次实际分类逐项比较。
分类版本仅在实际使用本地兜底时是必需证据；官方页面值使用页面证据，
不能强行赋一个本地 catalogRevision。
差异不通过时不能向下流发出可提交回执。

提交前再次执行 current 检查，核对账号身份、官方封禁、登录观察与最新控制意图。
封禁或掉登观察写入失败时，当前工具立即失败且不提交；
通过现有宿主持久停止机制阻断该账号或窗口后续写入，不能报告状态已保存。
在不可恢复存储错误期间停止该批次派发，恢复后先核对状态。

继续使用 `agent.action.prepare/get/unknown/confirm` 和稳定 operationId：
没有提交意图才允许创建一次，只有新的可执行意图才分派发布。
准备回执过期、表单被修改、租约变化或控制意图变为暂停，都需要重新验证。
提交后收到 106、超时或浏览器退出时，优先保留 `result_unknown`；
登录态可以同时显示掉登，但不能把条目改回“登录后重新发布”。

确认读取平台刊登 ID、账号、内容、价格、币种、时间和提交前基线。
查到已确认回执就返回原事实，无法唯一确认则等待处理。
确认事实与 outbox 事务保存，商品插件写入失败只重试同步。
同一账号的任何窗口存在未知提交时阻断后续写任务，直到核对完成。

## 6. 数据、协议和现有任务升级

拟新增的数据由各自所有者保存：

- 插件资源：规范分类文件及内容 revision。
- 商品库：带市场范围的候选分类及确认属性，受商品修订约束。
- 账号池：主页、逐窗口登录观察、独立 Money、收款列表、分域检查结果与分析证据。
- Rust SQLite：无浏览器准备任务与批准回执、`login_required`、发布工具阶段、
  冻结资料和页面实际分类、规则版本与准备回执；沿用原有发布意图和 outbox。

所有字段按现有约定明文保存，不写 Keychain。
普通日志只记状态、工具阶段、分类 ID、耗时和可公开错误，不记录凭据或完整 current。
图片、完整目录和敏感模型输入不复制进 SQLite 检查点。
银行完整记录也不复制进检查点或普通 Agent 快照，账号池投影必须显式排除。

升级在启动时执行一次事务，不引入两种业务契约的运行时兼容读取：
旧账号没有窗口登录观察时初始化为未检查，不批量假定掉登或已登录。
旧待执行批次在新工具规则下重新确认后创建新快照；
旧执行中且尚未提交的任务暂停并标记需要重新准备，不直接重放新的阶段。
旧已提交、未知和已确认任务保留原意图，只走结果核对及 outbox；
不能因换工具版本丢弃操作记录。历史事实继续只读显示。
旧任务图片/文案审核不沿用为新准备阶段批准；未提交条目重新准备后再入队。
旧余额按已知币种和逐项证据升级，新收款列表默认为未检查，不能初始化为“未绑定”。

新的 DTO 与公开 schema、Rust 校验、列表查询、状态筛选、通知、
配置与业务迁移同步修改，不增加 `logged_out` 到四种业务状态的别名分支。
`login_required` 是作业状态，`logged_out` 是窗口登录观察，两者名称与作用分开。
