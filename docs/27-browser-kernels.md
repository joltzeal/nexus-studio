# 浏览器内核下载与本地缓存

## 页面与操作

「应用设置 → 浏览器内核」只提供最新内核的下载入口、本机已安装版本、平台架构和缓存目录。
先在「激活码」页保存激活码，再下载或创建窗口；不要求用户安装 CLI、Node.js 或配置环境变量。
页面不回显激活码，也不再提供内核类型切换或手填版本。

刷新只读取本地安装清单，不连接下载服务、不创建窗口。浏览器预览显示桌面应用入口提示，
不模拟下载结果。清单只识别 SDK 的 `chromium-<完整版本>-pro` 安装目录，
目录中必须存在非空、可执行的当前平台浏览器文件；未完成下载和其他目录不会进入清单。

下载按钮在原生后台准备内核，页面显示实际下载百分比、传输量以及校验、解压、重试阶段。
SDK 未报告传输量时只显示阶段，不生成估计进度。离开设置页面不会取消后台准备；
返回页面后重新读取当前任务。应用退出后任务不会继续，重新打开时以磁盘清单为准。

## 数据与命令

Rust 的 `KernelService` 托管 Node 适配器，提供两个命令：

| 命令              | 输入               | 结果                                               |
| ----------------- | ------------------ | -------------------------------------------------- |
| `kernel_status`   | `refresh: boolean` | 本地目录、平台、安装清单、激活码配置标志和当前任务 |
| `kernel_download` | 无                 | 成功准备后的实际内核版本；失败返回可操作错误       |

命令错误以 `{ code, message, retryable }` 返回；前端仅展示结构化消息，
不把未知桥接错误或原始日志当成用户文案。

清单通过适配器的 `inventory` 操作离线读取，按数字版本倒序排列。
只有包含可执行文件的完整目录才进入清单；忽略 SDK 的临时解压目录。
清单检查不代替 SDK 下载时的签名和校验和验证，也不证明浏览器已能正常启动。

下载与窗口创建共用同一个服务、准备锁和应用数据目录下的 `cloakbrowser/` 缓存，
避免同一应用中多个请求争抢下载与解压。任务进行中再次请求准备会返回等待提示。
读取清单不会占用准备锁；轮询当前任务使用内存状态，不在每次轮询时启动 Node。
任务状态是内存状态，内核文件保存在磁盘，激活码继续由 Rust 从明文 SQLite 读取。

## 适配器协议

Node 使用固定 SDK 的公开 `ensureBinary` 接口获取内核，完成后执行二进制 `--version`，
把实际路径和版本返回 Rust。进度与错误走 stderr 的结构化行：

```text
NEXUS_KERNEL_PROGRESS {"phase":"downloading","percent":39,"downloadedMb":63,"totalMb":162}
NEXUS_KERNEL_PROGRESS {"phase":"verifying"}
NEXUS_KERNEL_ERROR {"code":"NETWORK","message":"…","retryable":true}
```

SDK 原始日志不能直接展示为用户错误。适配器沿 `cause` 链提取网络错误类别，
使用固定文案，不回显请求 URL、令牌、密钥或任意上游报文。
Rust 同时排空 stdout 和 stderr，避免下载过程因管道写满卡住，并限制保留输出的大小。
单次准备总期限为 12 分钟；超过期限会结束适配进程并返回超时。

瞬时网络或服务不可达错误最多尝试三次。签名、校验和、版本绑定以及权限失败
不自动重试，不跳过 SDK 校验。404、校验清单获取失败、激活码问题和网络问题分开反馈。
不把所有 `Pro binary unavailable` 包装错误统一显示为“稍后重试”。

应用代理预加载模块同时作用于激活码校验和内核准备，见[应用代理](26-application-network-proxy.md)。
选择的代理不可达时不能自动改成直连。

## 与窗口的关系

新建和批量创建窗口都由后台解析最新稳定内核，接口不再接收内核类型或用户指定版本。
`KernelService::prepare(None)` 从 SQLite 读取必需的激活码，调用 SDK
`ensureBinary(key, undefined, 'stable')`。SDK 负责解析新版与缓存复用；未填激活码时，
Rust 在启动适配器之前直接返回错误，Node 层也在调用 SDK 之前拒绝空密钥。
SDK 返回的二进制还必须属于受管安装清单，不能接受其他下载通道或任意本机文件。
上游不可达时仍遵循 SDK 的新版缓存策略；不因此承诺每次联网都能立即取得服务器最新发布。

创建完成后，窗口绑定实际二进制路径和 `--version` 显示版本。
启动和快照同样要求激活码、受支持的本机内核路径，以及与原绑定完全相同的显示版本。
这些操作关闭 SDK 自动更新，仅使用绑定二进制；下载新内核不会重绑已有窗口或改变指纹种子。
编辑表单不提供内核切换。旧公开内核的窗口不再支持启动、导出或迁移，需重新创建；
程序不自动转版本，不迁移或删除原浏览器数据目录。

内核包修订号和 Chrome 显示版本可能不同，例如合成测试中的包 `155.0.8059.39.2`
只报告 `155.0.8059.39`。本机清单保留完整包版本；迁移按完整版本准备并再次核对，
不能用相同 Chrome 显示版本的另一修订替代。
精确版本获取仅用于已有受支持窗口的导入恢复，不是新建窗口的选择项。
若 SDK 或激活码对应计划无法取得原包，导入失败，不换成最新包继续恢复。
迁移格式已升级，见[窗口加密迁移](28-window-transfer.md)。

## 问题排查与证据边界

“激活码已保存”只表示应用持有一条通过 SDK 校验流程的记录，不能证明本次网络能够
访问内核文件或校验清单。SDK 可能使用本地激活状态缓存；新机器缺少内核缓存时，
下载服务器、平台构件、网络代理及校验文件链路的故障才会首次暴露。

2026-10-23 在本机 macOS arm64 使用最终应用包中的 Node 和空临时缓存，
完成新版内核的真实下载、Ed25519 签名校验、SHA-256 校验和解压。
这说明 SDK 支持首次自动下载，不能据此断言用户新机器报错只是“没有提前下载”；
也不能据此认定 Windows 或用户网络环境通过验证。

实际代码检查与历史安装包结果记录在[质量与验证](09-quality-and-testing.md)。
