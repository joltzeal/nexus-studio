# 插件页面与长期插件系统

邮箱管理插件 `studio.email` 以独立的 `email.provider` 能力接入，提供微软邮箱
四段式导入、分页管理、Graph/OAuth IMAP 收信和持久化 token 刷新。
当前开发版本另有独立定时收信、已读未读同步、格式化阅读和账号池关联，
已发布 `1.0.0` 仍以原有只读收信为基线。
它不复用账号池的窗口生命周期，也不参与窗口迁移。
专用页面随主程序一起交付，具体范围见[邮箱插件](41-email-plugin.md)。

商品管理插件 `studio.products` 以独立的 `product.catalog` 能力接入，
提供商品资料、图片副本、分页、手动创建、文件导入、生图整组导入及已确认发布历史。
商品身份与 AI 生成记录分开；Ecom Agent 从商品库固定执行快照。
发布事实与准备状态分开，保留使用窗口，不把分配或模拟执行当成平台成功。
源码已接入，尚未发行，最低核心版本为 `0.1.29`，见[商品插件](43-products-plugin.md)。

Ecom Agent 插件 `studio.sales-agent` 声明 `sales.agent`，以 LangGraph.js
推进账号检查、商品上架和指定会话消息。批次、租约、检查点、动作日志和
发布同步和通知 outbox 由 Rust 持久化；插件只能通过当前作业 scope 调用受控工具。
Rust 同时保存控制修订、草稿模板、模型许可与用量，负责受保护历史清理。
专用页面提供商品分配、模型设置、运行前检查、分页任务、审查与人工接管，
实现与未验证边界见[Ecom Agent](44-sales-agent-architecture.md)。

插件开发者的具体 manifest、能力接口、目标宿主协议与验收要求见
[插件对接开发规范](14-plugin-integration-guide.md)。本文侧重产品现状与长期边界。

## 当前插件页面

2026-11-19 增加 Profile 表格的插件声明入口与通用右侧面板源码。
宿主提供协议、会话和 ShardX UI Kit 渲染，插件通过 manifest 和
`ui.view.*` 管理自身面板。没有入口声明时自动隐藏插件列及其菜单项。
本地 Vinted 示例提供关联、创建、编辑、联系方式确认、解绑、SIM8 分配、邮箱关联、
短信和邮箱验证码等待及语音、直接展示的衣柜快照。跨插件调用和任务状态走通用 UI 声明。
完整页面及安装后的原生执行仍有独立验收边界，详见
[设计](superpowers/specs/2026-11-19-profile-plugin-panel-design.md)。

插件中心是四个固定主页面之一。desktop-v2 已使用 ShardBrowser 页面骨架接入真实
Rust 插件命令，页面由 `PageHeader`、`SegmentControl`、`DataList` 和 UI Kit 弹窗组成。
“已安装”与“插件商店”共享紧凑表格，列为插件、能力、版本、状态或说明，以及操作。
操作覆盖本地安装、商店安装、单项更新、全部更新、授权、清单详情、发布信息、商店设置与卸载。
进程启动与退避重试由宿主管理，页面生命周期控件为安装和卸载。
安装是唯一的生命周期决策——装上即启用，并一次性获得 manifest 声明的全部能力；
应用启动时宿主会把已安装插件全部拉起，进程退出后由监督线程按退避自动重启，
第一方插件额外需要独立有效的签名租约；未激活或过期时宿主显示授权状态并停止进程。
安装、进程启动、RPC 和 Agent gateway 均由 Rust 宿主按插件 ID 检查租约，
不依赖插件自行判断。第三方插件不根据 `studio.` 前缀推断为付费插件。
表格使用中性图标块和语义状态 Badge。加载、空目录、商店未配置、搜索无结果和错误均使用
ShardX UI Kit 状态组件。详细视觉规则见
[插件中心设计规范](superpowers/specs/2026-11-18-raccoon-plugin-center-design.md)。
完整页面交互见[演示页面](11-demo-pages.md)，宿主行为见[插件宿主](17-plugin-host.md)。

### 二级导航与插件页面

侧栏读取 `plugin_catalog`，仅显示 `enabled: true` 且状态不是 `available` 的记录，
以插件 ID 作为路由标识、宿主返回的名称作为标签，并按 ID 稳定排序。
启动中或重试中的插件保留入口，未授权的第一方插件不进入侧栏；
页面展示实际状态，未安装的商店条目不进入侧栏。
安装、更新或卸载成功后立即重读目录，窗口重新获得焦点时刷新，
并每 5 秒检查一次后台状态；读取期间不叠加请求，安装前发出的旧响应不能覆盖新目录。
读取失败保留上一次菜单并显示“重新读取插件列表”。当前插件被卸载时回到插件中心。
纯浏览器预览没有宿主，因此不展示虚构的已启用插件入口。

`features/plugins/plugin-page.tsx` 只登记随主程序发布的专用 React 页面，
当前包含代理池、地址生成器、共享货源、AI 生图、Vinted 账号、SIM8 接码、Vinted 监控、邮箱、商品管理和Ecom Agent。
其他已启用插件也会出现在侧栏，点击显示名称、版本、状态、能力与方法数量；
具有 `window.sync` 能力时提供“前往窗口管理”入口。
动态发现目录不等于动态加载插件前端代码：增加新的专用页面仍需更新主程序。

desktop-v2 的插件中心、九个专用业务页和未接入占位均沿用应用页头、内容边距和
ShardX Card。筛选、结果和分页位于同一张 Card；文本搜索用 Input，固定选项用
有标签的 Select，保持单行，窄窗口仅在工具栏内横向滚动。代理池的识别/风险范围及
商品监控的来源 ID/收藏数通过带计数的「更多筛选」访问。导航分区和批量操作不混入筛选。

## 当前工程基础

`packages/plugin-sdk` 保留 manifest、能力与权限声明契约。
Rust `core::plugin_host` 在其上实现发现、安装、登记表、受管进程与权限检查点。
`core::plugins` 的内存登记表保留为调度器侧的代理端口抽象，不再代表插件系统的全部能力。
插件以独立 Node.js 子进程运行，标准输出只承载逐行 JSON 协议。
manifest 在安装时严格校验并据此授予能力，调用前逐项检查。
密码由插件明文保存在自己的私有目录，宿主不读取；`secretRef` 只在插件内部使用。
当前发布流程从用户配置的插件商店读取加密包，宿主负责下载、校验、安装和后台检查。
当前执行范围为维护者控制来源的受信任插件。

`plugins/proxy-pool` 是一个已实现的代理插件包：它按第 7 节协议提供 RPC 服务端，
具备私有存储、密钥引用、检测与订阅能力，安装后即可作为窗口的代理来源，
见[代理池插件](15-proxy-plugin.md)。

`plugins/vinted-helper` 的 `address.generator` 能力提供地图选点资料、用户名生成、
地址保存、CSV 与本地 A6 面单提取，desktop-v2 已接入专用页面；Overpass 查询已移除，见[VInted helper 插件](19-address-generator-plugin.md)。
v2 地图使用主程序构建注入的浏览器 Key，不从插件密钥槽读取；地址显式保存后写入插件私有文件。

`plugins/shared-supply` 是第三个已实现的插件包：`supply.catalog` 能力提供分类商户、商品搜索、
以图搜图与本地收藏，见[共享货源插件](21-shared-supply-plugin.md)。
它不需要任何密钥槽，收藏写在插件私有目录。

`plugins/ai-image` 是第四个已实现的插件包：`image.provider` 能力提供 OpenAI 官方与兼容接口的
生图改图、参考图文案与生成记录，见[AI 生图插件](22-ai-image-plugin.md)。

`plugins/vinted-monitor` 是第五个已实现的插件包：`monitor.collector` 能力按间隔采集 Vinted
搜索页或会员衣柜，留下运行记录与去重后的商品归档，见
[Vinted 监控插件](23-vinted-monitor-plugin.md)。它同样不需要密钥槽。

`plugins/vinted-accounts` 是第六个已实现的插件包：`account.pool` 能力保存账号记录、
解析 CSV/XLSX 导入并维护账号与浏览器窗口的关联，见
[Vinted 账号池插件](24-vinted-accounts-plugin.md)。它不发起网络请求，也不需要密钥槽。

`plugins/sim8` 实现 `verification.provider` 能力：按 SIM8 接口买号、取码、同步订单与
筛选检测，并把号码与接码链接写进 Vinted 账号池，见 [SIM8 接码插件](30-sim8-plugin.md)。
它是第一个真正用到这个能力的插件，API Token 存在自己的密钥槽里。

仓库内存在插件实现不等于插件系统已经通用可用：只有 `proxy.provider`、`address.generator`、
`supply.catalog`、`image.provider`、`monitor.collector`、`account.pool` 与
`verification.provider` 具备真实调用路径；
`platform.adapter` 与 `environment.configurator` 仍只有声明与类型。

## 长期首阶段信任模型

当前真实插件只考虑受信任 TypeScript 代码，通过独立 Node.js 进程承载。
维护者控制代码来源、版本与依赖，并保留可追溯记录。
独立进程有助于生命周期与故障管理，本身不能证明恶意代码被限制。
manifest 和 permissions 是描述与授权契约，不是操作系统沙箱。
没有额外措施时，Node.js 代码可能访问进程用户可访问的文件与网络。
不得向用户承诺未经实现的文件、网络或系统隔离保障。
当前不开放任意第三方插件执行。

## 后续 SDK 与 manifest 契约

SDK 仅暴露稳定能力，不透出 SQLite 连接、Rust 内部结构或引擎对象。
请求需明确输入、结果、错误、取消与超时语义。
协议版本与兼容范围应可校验，不兼容时拒绝执行。
manifest 应表达插件标识、版本、入口、兼容范围与所需能力。
具体字段以实际 contracts 和 SDK 为准，文档不另建平行 schema。
声明必须对应宿主检查点，没有执行检查的字段不能称为强制权限。
manifest 不嵌入账号凭据、访问令牌或代理密码。
安装记录持久化不等于 manifest 已验证或权限已落实。

## 宿主生命周期

宿主区分发现、安装、启动、可调用与重试中，页面状态由这些检查派生。
进程初始化成功不代表浏览器、账号或业务任务已经可用。
崩溃、超时与启动失败返回明确错误，并结束未完成调用；
进程退出后由监督线程按退避自动重启，不把失败留给用户处理。
停止先尝试协作退出，再按受控策略结束进程与回收资源。
取消必须有确定最终状态，取消后不能继续反馈执行成功。
重复请求是否可重试随实际能力定义，不默认所有调用幂等。
插件退出不得破坏其他页面或工作空间的数据。

## 数据与浏览器边界

插件通过宿主提供的私有目录持久化，不直接持有授权 SQLite 写入权。
插件不能枚举或读取 CloakBrowser 授权记录。
密码是插件私有目录里的明文文件，不经过宿主，也不做加密或隔离；
调用入口的授权检查不等于网络或文件隔离。
浏览器调用遵守不可变启动快照、profile 独占锁和必需代理失败阻断。
插件不能通过自己的路径绕过代理或抢占 profile。
会话与标签页的资源限制分别定义，不共用未经验证的配额解释。
详细规则见[浏览器接入](05-browser-integration.md)与[本地数据](07-data-storage.md)。

## 第三方开放与验证

开放前需落实隔离方式、来源验证、文件与网络访问边界及更新完整性。
应明确哪些限制来自宿主协议，哪些来自操作系统或执行环境。
若继续采用受信任进程，产品说明必须准确表达这一信任范围。
当前测试覆盖宿主安装即启动、能力拒绝、调用、崩溃后自动重启、旧登记表补齐、卸载与启动阻断，
以及页面状态、持久化与 SDK 契约行为。
真实代理链路、真实浏览器启动与 Windows 行为尚未验证。
插件和运行时的授权与打包约束见[分发](08-distribution.md)。
[质量矩阵](09-quality-and-testing.md)由主线填写，不将页面状态测试视为插件安全验证。
